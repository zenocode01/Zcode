# Zcode 本地小模型优化 — 设计草案

> **状态**：草案，待审阅。确认后再决定并入 `docs/基本构思.md` 或单独成篇。
> **目标模型档位**：14B-32B 级本地模型（Qwen2.5-14B/32B、GLM-4-9B、Llama-3.1-8B/70B 等），消费级硬件本地推理。
> **优化范围**：记忆层本地化、技能内容精简、推理框架适配。
> **事实依据**：mem0 源码调查（见文末"事实附录"），非臆测。

---

## 一、小模型能力画像（设计的出发点）

14B-32B 级本地模型与前沿云模型相比，五个关键差异决定了全部优化方向：

| 能力维度 | 云前沿模型 | 14B-32B 本地模型 | 对本项目的影响 |
|----------|-----------|-----------------|---------------|
| 上下文窗口 | 100K-200K+ | 8K-32K | 技能注入必须"按需加载"，不能全量堆 |
| 指令遵循 | 强，长指令也能执行 | 中等，复杂多条件指令易走样 | 技能文件要短句、单职责、步骤少 |
| JSON/结构化输出 | 稳定 | 不稳定，易漏字段、非法 JSON | 输出格式要极简；JSON 场景需容错兜底 |
| 工具调用 | 原生 tool calling，稳定 | 弱，schema 遵循差、易幻觉工具名 | 三层降级策略（见 §四） |
| Token 成本 | 贵 | 便宜但算力慢 | LLM 只用在必须处，检索零 LLM |

**三条总原则**：
1. **LLM 只用在必须的地方**：提取/总结类任务才调用模型；检索、去重、排序尽量走确定性代码。
2. **把"智能"前置到规则里**：能用模板、检索、规则树表达的，不指望模型自由发挥（对应 MetaSkill 的本地模式化）。
3. **同一套技能格式，双版本内容**：标准版（云）+ 精简版（本地），通过 profile 机制切换，不搞两套体系。

## 二、记忆层本地化（重点）

### 2.1 本地"三件套"选型

基于 mem0 OSS 的实际支持面（`mem0/llms/configs.py`、`mem0/embeddings/configs.py`、`mem0/vector_stores/configs.py`）：

| 组件 | 推荐 | 备选 | 关键配置 |
|------|------|------|---------|
| 本地 LLM | Ollama | vLLM、LM Studio、llama.cpp server | `llm.provider=ollama` + `ollama_base_url`；或 OpenAI 兼容端点（`openai_base_url`） |
| 本地 Embedding | Ollama `nomic-embed-text`（起步）→ `gte-Qwen2-1.5B` 级（质量档） | HuggingFace / TEI、FastEmbed | `embedder.provider=ollama` + `embedding_dims` 一致 |
| 向量库 | **Qdrant 嵌入式**（默认即本地，且支持 BM25 混合检索） | Chroma（纯语义，更轻）、FAISS | `vector_store.provider=qdrant` + `path` 本地路径 |
| 历史库 | SQLite（mem0 默认 `~/.mem0/history.db`） | — | `history_db_path` |

**关键约束（来自 mem0 源码）**：
- **混合检索（BM25 关键词 + 语义 + 实体 boost）只有 `qdrant` / `pgvector` / `milvus` / `redis` 支持**；用 `chroma` / `faiss` 会自动退化为纯语义检索。因此**默认选 Qdrant 嵌入式**，否则本地记忆检索质量打折。
- Embedding 质量建议 ≥ Qwen 600M 级别（mem0 README 明确建议），`nomic-embed-text`（512 维）只能算起步档。
- 换 embedder 时 `embedding_dims` 必须与向量库已存数据一致，否则维度报错。

### 2.2 写入路径（add）—— 唯一 LLM 热点，重点优化

mem0 `add(infer=True)` 的流程中，**Phase 2 的单次 LLM 事实提取**是唯一调用模型的地方，且提示词很重：要求严格 JSON、语义去重、实体链接、相对时间锚定（`mem0/configs/prompts.py:468` 起）。14B-32B 模型在此步质量会明显下降（漏提取、JSON 非法）。

针对本地小模型的四级优化：

| 级别 | 做法 | 代价 |
|------|------|------|
| L0 兜底 | `infer=False`：完全跳过 LLM，原文直接 embedding 存储 | 无提取、无去重，记忆是"原始语录" |
| L1 默认 | 简化提取提示词：通过 `custom_instructions` / `prompt` 参数裁剪重要求（去掉 `linked_memory_ids`、相对时间锚定等），只做"提取事实 + 一句总结" | 提取质量略降，但小模型能稳定输出 |
| L2 增强 | 温度 ≤0.2 + 复用 mem0 已有的 `extract_json` / `remove_code_blocks` 解析降级 | 实现成本低，收益直接 |
| L3 批量 | 批量 add 合并为单次 LLM 调用（多条消息一次提取），减少模型调用次数 | 一次调用更长，需控制 max_tokens |

**写入频率策略**：本地场景下模型调用慢、贵在时间，所以**写入低频化**——只有会话结束、里程碑、用户显式触发时才落记忆，而不是每次交互都提取。

### 2.3 检索路径（search）—— 零 LLM，无需优化

mem0 OSS v3 的 `search()` **全程不含任何 LLM 调用**：查询直接做 embedding，预处理只是 CPU 侧的词形还原（供 BM25）+ 实体抽取（供 boost），无 query rewrite。可选 reranker（`sentence_transformer` 本地可用）默认关闭。

结论：**本地小模型对检索侧完全无压力**，本项目只需沿用，并把"多路召回（语义+BM25+实体）+ 融合打分"作为记忆检索的默认路径。

### 2.4 与 Layer 3 技能记忆的对接

技能级记忆（`.memory/`：`experience.log`、`improvements.md`、`context-snapshot.json`）在本地模式下的写入规则：

- **回写模板化**：用"固定的经验回写模板"（谁在用、场景、成功/失败、一句话教训）代替"让 LLM 自由总结"，模板由代码填充，不消耗模型 token。
- **低频批量回写**：本地模式下每 N 次技能使用（或会话结束）才聚合回写一次，避免小模型频繁空转。
- **快照规则化**：`context-snapshot.json` 由适配层按固定 schema 收集（项目路径、语言栈、上次目标），不依赖模型生成。

## 三、技能内容精简（面向 14B-32B）

### 3.1 精简规范（SKILL.local.md 的编写约束）

| 维度 | 标准版（云） | 精简版（本地） |
|------|-------------|---------------|
| 文件体积 | ≤ 8K tokens | **≤ 3K tokens**（14B 上下文 8K-32K，要给对话和工作内容留预算） |
| 步骤数 | 可 8-10 步 | ≤ 5-7 步，线性 |
| 句式 | 可含背景解释、多条件 | 短句、动词开头、单职责；砍示例、砍背景 |
| 条件分支 | 允许嵌套 | 显式扁平化（"如果 X → 做 A；否则 → 做 B"） |
| 输出 | 复杂结构 | **一行一字段**列表（`- 步骤: xxx`），避免嵌套 JSON |
| 兜底 | 隐含模型判断力 | **显式兜底动作**（"解析失败 → 原样输出并告警"） |

### 3.2 双版本机制

```
skills/<name>/SKILL.md          # 标准版（云端、强模型）
skills/<name>/SKILL.local.md    # 精简版（本地 14B-32B）
```

- 由 **profile**（见 §四）决定加载哪个版本：`zcode --profile local-14b` 或环境变量。
- 版本内容独立维护（精简版不是自动压缩，而是人工重写的"小模型向"指令集）。
- 技能引擎注入时：**只注入当前 profile 对应的版本**，另一版本不占上下文。

### 3.3 结构化输出的本地约束

- 记忆提取等**必须 JSON** 的场景：给"填空式"模板（字段固定、数量固定、可选字段砍掉），比自由 JSON 稳定得多。
- 其余场景一律用**极简列表格式**（`- 键: 值`），由适配层解析，模型输出任何近似格式都能容错。

### 3.4 MetaSkill 的本地模式

- **背景**：MetaSkill 把规则交给模型自由编排，14B-32B 容易编排乱。
- **本地模式默认走"确定性工作流模板"**：线性步骤 + 显式条件分支（`if/else`），模板由外部 runner 执行，模型只做"当前步该做什么"的决策。
- MetaSkill（自由编排）保留为云端强模型的可选增强，本地 profile 默认关闭。

## 四、推理框架适配

### 4.1 适配目标与统一抽象

| Provider | 协议 | 备注 |
|----------|------|------|
| Ollama | 原生 API + OpenAI 兼容端点 | mem0 有原生客户端；本项目以 OpenAI 兼容为基准 |
| vLLM | OpenAI 兼容（`/v1`） | 生产级吞吐 |
| llama.cpp server / LM Studio | OpenAI 兼容 | 轻量、单机 |

**统一基准**：OpenAI 兼容协议。Ollama 原生 API 作为可选直连优化（其 JSON mode、工具调用有原生字段）。

### 4.2 工具调用三层降级（核心适配逻辑）

小模型工具调用弱的表现：不遵循 tool schema、一次只调一个工具、参数错、幻觉工具名。对策分三层，按模型能力自动选择：

```
L1 原生 tool calling：模型声明支持 tools（Qwen 系列、GLM-4 等）
   → 直接映射到 OpenAI 兼容 tools 格式，走标准流程。

L2 提示词编码：模型无原生工具或 L1 实测不稳
   → 把工具调用"编码"进提示词：要求输出 <tool>名称</tool><args>JSON</args>，
     适配层用解析器提取；解析失败走 L3。

L3 无工具模式：解析仍失败 / 模型太弱
   → 工具调用内联进技能文件："如果输入匹配 X 模式 → 外部 runner 执行 Y 命令"，
     模型只做"该走哪条分支"的判断，不生成任何调用。外部 runner 负责执行与回填。
```

适配层通过 **tool level 探测**（一次性小基准：让模型调一个测试工具，看能否通过）自动定级，写入 profile。

### 4.3 Profile 机制（Layer 0 扩展）

`adapters/profiles/local-14b.yaml`（示例）：

```yaml
name: local-14b
model_family: qwen2.5-14b   # 或 glm-4-9b / llama-3.1-8b ...
context_window: 16384
tool_level: 1                # 0=无工具 1=提示词编码 2=原生 tool calling
json_reliability: low        # low → 优先极简列表格式 + 填空 JSON
skill_variant: local         # 加载 SKILL.local.md
memory:
  llm: {provider: ollama, model: qwen2.5:14b}
  embedder: {provider: ollama, model: gte-qwen2-1.5b, dims: 1536}
  vector_store: {provider: qdrant, path: ~/.zcode/memory}
  infer_mode: simplified     # 简化提取提示词（§2.2 L1）
  write_frequency: low       # 低频批量回写
```

Profile 是"能力声明"，技能引擎与记忆层据此决定：加载哪个技能版本、用哪种输出格式、走哪级工具降级、记忆怎么写入。

### 4.4 上下文管理（14B-32B 8K-32K 预算）

- **索引式注入**：启动只注入技能索引（名称 + 一句话用途），用户任务匹配到某技能时才读完整 SKILL 文件。
- **按需加载**：技能正文不进系统提示，只在激活时注入，用后即弃。
- **会话压缩**：技能指令放系统提示首位（高优先级）；工作日志只保留最近 N 轮 + 定期摘要。

## 五、与四层架构的融合

| 层 | 本地小模型增补 |
|----|---------------|
| Layer 0 适配层 | 新增 ollama / vllm / llama-cpp provider；OpenAI 兼容基准；工具三层降级；profile 机制 |
| Layer 1 技能库 | 双版本（SKILL.md / SKILL.local.md）；精简规范；按 profile 加载 |
| Layer 2 编排 | 本地模式默认确定性工作流模板；MetaSkill 关闭或降级为线性模板 |
| Layer 3 记忆层 | mem0 本地三件套（Qdrant + 本地 embedder + Ollama/vLLM）；写入四级优化；检索零 LLM；回写模板化 |

## 六、落地路线（并入现有路线图）

| 阶段 | 增补内容 | 验收 |
|------|---------|------|
| Phase 1 | `adapters/` 增加 ollama/vllm provider 与 OpenAI 兼容基类；`adapters/profiles/local-14b.yaml`；技能精简规范 v1 | 一条 14B 模型命令能加载 profile 并注入精简技能 |
| Phase 2 | 确定性工作流模板先行；工具三层降级实现 | 弱工具模型跑通"功能开发"模板（含降级路径） |
| Phase 3 | mem0 本地三件套配置模板；写入四级优化；回写模板化 | 本地记忆闭环：add → search → 命中 |
| 持续 | 本地小模型基准集（JSON 稳定性、工具调用成功率）纳入技能质量评估 | 每模型档位一份评估报告 |

**最小闭环验证**（Phase 1+3 合并快速验证）：
```
Ollama + Qwen2.5-14B（或 GLM-4-9B）
→ mem0 本地三件套（qdrant 嵌入式 + gte embedding）
→ 写入一条技能使用经验 → search 命中
→ 加载一个精简技能（如 tdd-local）跑一次任务
```

## 七、开放问题（待确认）

1. **记忆层实现**：直接引入 mem0（成熟、支持广）还是自建更轻的本地记忆（更贴本项目、可控）？草案按"以 mem0 为参照、接口兼容自建"编写。
2. **精简版技能维护**：人工重写（质量稳）还是提供"精简生成器"脚本（省力但需验证）？草案默认人工重写。
3. **profile 粒度**：按模型家族（qwen2.5-14b）还是按能力特征（context/tool/json 三要素）？草案两者都有（能力声明为主，模型名作备注）。
4. **7B-8B 档**：当前按 14B-32B 设计；如需覆盖 7B-8B，主要变化是工具降级默认到 L2/L3、技能体积上限再砍半、记忆默认 L0/L1。

## 事实附录（mem0 调查要点，源码位置）

- 本地 LLM：`ollama` / `vllm` / `lmstudio` / OpenAI 兼容端点均可（`mem0/llms/configs.py`）；Ollama 原生客户端默认 `http://localhost:11434`。
- 本地 embedding：`ollama`（默认 `nomic-embed-text`）、`huggingface`（sentence-transformers/TEI）、`lmstudio`、OpenAI 兼容、`fastembed`（`mem0/embeddings/configs.py`）。
- 向量库 25 个 provider，本地友好：`qdrant`（默认嵌入式 `/tmp/qdrant`）、`chroma`、`faiss`；**BM25 混合检索仅 qdrant/pgvector/milvus/redis 实现**（`mem0/memory/main.py:518-525`）。
- `add(infer=True)` 单次 LLM 提取 + 严格 JSON（`mem0/configs/prompts.py:468`）；`infer=False` 零 LLM。
- `search()` 全程零 LLM、无 query rewrite（`mem0/memory/main.py:1349-1701`）。
- 官方示例模型为 `mixtral:8x7b`、`llama3.1:8b/70b`、`Qwen2.5-32B-Instruct`——无 7B 以下示例。
- OpenMemory 已停更弃用，建议自托管 server（`openmemory/README.md`）。
