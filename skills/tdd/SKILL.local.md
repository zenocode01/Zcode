# tdd（本地精简版）

## 何时使用

- 用户要求开发新功能或修 Bug 时

## 启动门槛（每次开始前先确认）

1. 反馈回路就绪：测试框架可运行、一次测试在数秒内出结果；没有 → 先搭最轻量框架（pytest/vitest），禁止在无反馈状态下直接动手
2. 场景不豁免：紧急修复先写复现测试（红）再修；性能优化先写基准/特征测试再改
   —— 跳过测试直接改 = 主动引入回归风险

## 工作流程

1. 写一个失败测试（最简场景）
2. 跑测试，确认失败（红）
3. 写最小实现，让测试通过（绿）
4. 重构：清理重复与命名，保持测试全绿
5. 回到步骤 1 写下一个测试，直至功能完整；最后跑全量测试

## 输出格式

- 测试: <文件路径>
- 实现: <文件路径>
- 结果: <通过数>/<总数>

## 兜底

- 无测试框架 → 先搭最轻量框架（pytest/vitest）
- 需求模糊 → 先问用户验收标准，再开始循环
- 测试全红无法前进 → 停止，向用户报告卡点
