# tdd — 测试驱动开发（标准版）

## 何时使用

- 用户要求开发新功能、实现需求时
- 用户要求修复 Bug（先写复现测试）
- 代码库已有测试框架，但新代码未覆盖测试时

## 工作流程

1. **红（写失败测试）**：先写一个描述期望行为的测试，运行确认它失败。
   - 从最简单、最有价值的场景开始，一次只写一个测试
   - 测试应只依赖公开行为，不测试实现细节
2. **绿（最小实现）**：写恰好让测试通过的最少代码。
   - 不提前设计、不写用不到的抽象
   - 允许"丑陋但通过"，重构放在下一步
3. **重构（清理）**：在测试全绿的保障下，消除重复、改进命名、提取合理抽象。
   - 每步重构后立即跑全量测试，保持全绿
4. **重复循环**：回到步骤 1 写下一个测试，直到行为完整覆盖。
5. **验证收尾**：跑全量测试套件 + 静态检查，确认无回归。

## 关键约束

- 任何"实现代码"必须先有"失败测试"兜底，禁止先写实现再补测试
- 启动前确认反馈回路就绪：测试框架可运行、反馈快（数秒内出结果）；无框架先搭，禁止在无反馈状态下直接动手
- 紧急修复 / 性能优化不豁免 TDD：先写复现测试（bug）或特征/基准测试（遗留系统/性能）锁定现状，再改；跳过测试直接改 = 主动引入回归风险
- 一次只让一个测试从红变绿，避免大步子
- 重构阶段不得新增功能行为

## 输出格式

- 测试文件路径：<path>
- 测试用例清单：<用例名> → <期望行为>
- 实现变更：<文件> → <改动摘要>
- 测试结果：<通过数>/<总数>

## 兜底

- 已有代码无测试框架 → 先搭最轻量的框架（pytest / vitest 等）再开始
- 测试难以编写（如遗留系统） → 先写特征测试（characterization test）锁定现状，再逐步重构
- 需求本身模糊 → 停止 TDD 循环，先向用户澄清验收标准
