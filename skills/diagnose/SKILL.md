# diagnose — 系统化调试（标准版）

> 移植自 Matt Pocock 技能集（diagnosing-bugs）。

## 何时使用

- 用户报告代码 broken / throwing / failing / slow（含性能回归）
- 用户说 "diagnose" / "debug this"

## 工作流程

1. **构建反馈回路（核心，投入不成比例的精力）**：按顺序尝试：失败测试 → curl/HTTP 脚本 → CLI+fixture 快照 → 无头浏览器 → 重放捕获 trace → 一次性 harness → property/fuzz 循环 → 二分 harness（`git bisect run`）→ 差分循环 → HITL bash 脚本（最后手段）。然后收紧回路：更快、信号更尖锐（断言确切症状而非"没崩"）、更确定。
2. **复现 + 最小化**：必须复现用户描述的**确切症状**；逐个削减输入/配置/步骤，直到每个剩余元素都"承重"（删掉任一即变绿）。
3. **排序假设**：列出 3-5 个可证伪的假设（格式："如果 X 是原因，那么改 Y 会让 bug 消失/更糟"），**展示给用户后再测**；无法陈述预测的假设是"vibe"，丢弃。
4. **插桩**：每个探针对应一个预测，**一次只改一个变量**；调试器/REPL 优先于日志；每条调试日志带唯一前缀 `[DEBUG-xxxx]`（清理时一次 grep）。
5. **修复 + 回归测试**：**修复前先写回归测试**（仅当存在正确 seam——测试真实调用点模式；无正确 seam 本身就是发现）。
6. **清理 + 复盘**：确认原复现消失、回归测试通过、`[DEBUG-*]` 全部清除、临时原型删除；最后问"什么能防止这个 bug？"——若答案是架构问题（无测试 seam、缠绕耦合），交接给 improve-arch。

## 硬规则

- **没有能红的紧致命令，就没有下一阶段**——"跳过直接假设"正是本技能要防止的失败
- 错 bug = 错修复：必须先复现确切症状
- 修复前先写回归测试（除非无正确 seam）

## 输出格式

- 复现命令：<命令>
- 根因：<假设 + 证据>
- 修复：<文件 → 改动>
- 回归测试：<路径>
- 复盘：<什么能防止 + 是否交接 improve-arch>

## 兜底

- 构建不了回路 → 明说、列出已尝试方式、向用户要环境/工件/临时生产插桩权限
- 非确定性 bug → 目标改为提高复现率（50% 可调试，1% 不可）
- 回路 30 秒且 flaky → 几乎等于没有；2 秒确定性才算紧
